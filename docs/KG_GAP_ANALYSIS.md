# KG multi-hop gap analysis

_Generated by `python -m evals.analyze_kg` against the live Neo4j index
(397 chunks / 1,544 entities / 1,264 RELATES edges); raw data in
`evals/results/kg_gap_analysis.json`. Retrieval-only: no LLM calls._

## Question

METRICS.md showed multi-hop end-to-end scores stuck (~1.64/2 for both
`hybrid` and `hybrid+kg`) while multi-hop Recall@5 read ~90–100%. Before
building more graph machinery (two-hop expansion, better entity linking),
this analysis answers: what does `graph-expand`'s bridge actually change
on the six golden multi-hop questions?

## Measured result (k=5)

| id    | bridge slots | filled | golden-source hits in bridge | hybrid missed a source | recovered |
|-------|--------------|--------|------------------------------|------------------------|-----------|
| tra-01| 2            | 2      | 0                            | no                     | —         |
| mh-03 | 2            | 2      | 0                            | no                     | —         |
| mh-04 | 2            | 2      | 0                            | no                     | —         |
| mh-05 | 2            | 2      | 1                            | yes (Knowledge_graph) | Knowledge_graph |
| mh-06 | 2            | 2      | 0                            | no                     | —         |
| mh-08 | 2            | 2      | 0                            | no                     | —         |

Summary: slot fill rate **1.00**; 1/6 questions had a bridged chunk
containing a golden snippet; 1/6 questions had any golden source missing
from hybrid's top-5 — the same question (mh-05), and the bridge recovered
exactly that source.

## Findings

1. **Entity matching is not the bottleneck.** Bridge slots fill 100% of
   the time; the query→entity→chunk walk never comes back empty.
2. **The second-source gap is nearly gone at retrieval level.** Plain
   hybrid's top-5 already contains every golden source for 5 of 6
   multi-hop questions. There is little left for the graph to fix here.
3. **When the gap exists, the bridge closes it.** mh-05's missing source
   (Knowledge_graph.txt) was surfaced by a bridged chunk that carries a
   golden snippet — the mechanism works precisely as designed, and the
   cost is noise (irrelevant bridges) on the other five questions.
4. **Therefore the remaining multi-hop deficit is in generation**, not
   retrieval: all sources arrive in context, yet judged answers still
   average ~1.64/2. Synthesis across two documents is the failing stage.

## Decision

Deferred indefinitely:
- two-hop expansion — nothing to recover; bridges already fill and the
  extra hop would only add noise;
- improved query-time entity linking — match rate is already 1.0.

Candidate next experiment instead: **generation-side synthesis** for
multi-hop answers (e.g., per-source sub-answer prompting before final
composition, comparing answers judged with vs without it on the
`multi_hop` slice). Note self-judge bias applies to all e2e numbers.

## Caveats

- Six questions: the margin between 5/6 and 6/6 is one labeling choice.
- Bridge hits are measured against golden snippets — bridged prose can be
  useful without verbatim-snippet overlap; b-hits=0 rows are weakly
  informative individually, strongly informative in aggregate.
- This analyzed retrieval only. Generation behavior needs `run_e2e`
  plus the runs.jsonl diagnostics added alongside this script
  (`retriever_diagnostics` on every RunRecord for graph-expand queries).
